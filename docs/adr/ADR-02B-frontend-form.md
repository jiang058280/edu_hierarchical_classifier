## 背景

计划最初按 12 个 HTML 页面评估。截至本次盘点，`static/` 中已有 17 个 HTML 页面，其中教师业务 8 个、学生业务 5 个，另有门户、登录、分类工具和治理台。教师端与学生端已分别通过 `teacher_common.js`、`student_common.js` 复用认证、请求、导航与消息提示，视觉规则集中在 `edu.css`。

当前主要问题不是缺少组件框架，而是部分新增页面仍使用行内样式、脚本集中在单页、缺少统一浏览器自动化环境。此时整体迁移 Vue3 会同时改变路由、构建、部署、缓存和调试方式，并扩大 RAG 与教学闭环的回归范围。

## 决策

M4 结束时继续使用原生 HTML/CSS/JavaScript，不引入 Vue3、Node 构建链或第二套前端运行时。

后续新增页面遵循以下边界：

1. 认证、API、导航和通知继续放入公共脚本，禁止复制出第三套实现；
2. 跨两个页面复用的视觉规则进入 `edu.css`，逐步减少行内样式；
3. 页面脚本只负责交互与渲染，计算、权限和数据过滤必须留在服务端；
4. 所有页面保留 `viewport` 声明，学生端以 375px 无横向溢出为验收条件；
5. 恢复 Playwright 环境后优先补浏览器回归，而不是立即迁移框架。

## 重新评估 Vue3 的触发条件

满足以下任意两项时重新立项评估：

- HTML 业务页面达到 25 个；
- 同一复杂交互组件在 3 个以上页面重复维护；
- 出现需要前端全局状态协调的实时课堂、协同编辑或离线学习；
- 单页脚本超过 800 行且拆分后仍难维护；
- 前端专职人员加入并有稳定 Node 构建、测试与发布流水线。

## 后果

短期避免无业务增益的全量重写，部署仍由 FastAPI 直接提供静态资源。代价是需要持续治理公共样式和单页脚本；E6 之后应把浏览器自动化依赖固定下来，并优先覆盖登录、作答、RAG 问答和移动端四条主链路。
