## 一、目标图景：从分类器到平台

### 1.1 一句话定位

> **教师用 AI 快速建设题库、布置作业；学生在线作答、自动沉淀学情；作答数据反哺题库质量与模型迭代** —— 这条闭环就是"智慧教研平台"的主轴。

### 1.2 业务闭环图

```
                    ┌──────────────── 教师端（教研）────────────────┐
                    │  AI 录题 → 人工确认 → 题库（学段/难度/知识点）    │
                    │  智能组卷 → 试卷库 → 布置作业/考试（到班级）      │
                    └───────────────┬───────────────┬──────────────┘
                                    ▼               │
   ┌────────────── 学生端（学习）──────────────┐      │
   │  我的作业 → 在线作答（客观题自动判分）        │      │
   │  错题本（自动生成）→ 重练 + 相似题推荐       │      │
   │  我的学情（知识点掌握度/趋势）               │      │
   └───────────────┬──────────────────────────┘      │
                   ▼                                  ▼
        answer_records 作答数据 ──► 学情分析（学生/班级/知识点三维）
                   │                                  │
                   ▼                                  ▼
        错误率高的题目/知识点 ──────────► 题库质量复核（复核工作台）
                   │                                  │
                   ▼                                  ▼
        Bad Case 回流 ──► 模型再训练（已有闭环）──► 更准的自动分类
```

**平台的护城河不在功能多，而在数据闭环转起来**：每道题被越多学生作答，题目质量与学情分析越准；每次人工修正，自动分类模型越强（该闭环的录入端已在改进计划中打通）。

### 1.3 用户与场景

| 角色 | 谁在用 | 核心场景 | 使用终端 |
| --- | --- | --- | --- |
| 管理员 | 平台运营者/信息老师 | 账号审核、模型版本治理、全局统计 | 桌面 |
| 教师 | 初高中学科老师 | 录题建库、组卷、布置作业、看班级学情 | **桌面为主** |
| 学生 | 初高中学生 | 做作业、错题重练、看自己的学情 | **手机为主** |

## 三、总体架构：双门户 + 统一基座

保持**模块化单体**（不拆微服务，沿用企业级改造计划 D1 决策），前端按角色分门户：

```
                         ┌──────────── Nginx（HTTPS，生产阶段加）────────────┐
                         │   /            → 门户选择页（教师入口 / 学生入口）     │
                         ▼
        ┌──────── 教师端（桌面优先，蓝白教研风）────────┐  ┌──── 学生端（移动优先，卡片化）────┐
        │ /teacher/login                              │  │ /student/login                  │
        │ /teacher/  题库·录入·组卷·作业·学情·班级·复核   │  │ /student/  作业·做题·错题本·我的学情│
        └──────────────────┬───────────────────────┘  └──────────────┬──────────────────┘
                           │        同一 FastAPI 应用，路由按角色分组并校验门户        │
                           ▼                                        ▼
   ┌────────────────────────────── edu_core 单体基座 ──────────────────────────────┐
   │ api/teacher/*  api/student/*  api/admin/*（现有治理/统计路由归入 admin 组）        │
   │ application/（新增 AssignmentService / StudentService / AnalyticsService）      │
   │ security（RBAC 三角色 + 门户校验）   storage（现有 9 表 + 新增 8 表，见第六节）      │
   │ inference（分类模型 v0.2）  dedup（Milvus 查重 + 相似题推荐）  quality（门禁/评估） │
   └──────────────────────────────────────────────────────────────────────────────┘
```

**关键原则**：
1. **一套后端，两个门户**：账号、题库、模型都是同一基座；"分开"体现在登录入口、界面、路由权限三个层面（详见第四节），而不是两套系统——两套系统会造成题库与学情数据割裂，违背闭环初衷；
2. **路由前缀即权限边界**：`/api/v1/teacher/*` 与 `/api/v1/student/*` 在依赖层强制校验角色，教师 token 调学生接口（及反向）直接 403；
3. 现有 `/classify`、`/stats` 等路由归组收编，旧路径保留别名兼容。

## 四、登录系统分离设计（核心需求）

### 4.1 "分开"的三层含义与落地

| 层面 | 设计 |
| --- | --- |
| **入口分开** | 两个独立登录页：`/teacher/login`（教师门户，蓝白教研风）与 `/student/login`（学生门户，明快配色、大按钮）；门户选择页 `/` 提供两个醒目入口 |
| **账号分开** | 同一张 `users` 表、同一个 JWT 签发服务，但 **role 严格区分**（admin/teacher/student）；教师账号只能由管理员或其他教师创建，学生账号由教师通过"班级邀请码 + 名册"创建/导入；**账号不通**：学生无法从教师门户登录（反之亦然），登录时校验 `role ∈ 门户允许集合`，不匹配直接拒绝并提示"请从正确门户登录" |
| **界面分开** | 登录后按角色进入完全不同的界面（教师教研工作台 vs 学生学习端），共用登录态机制（JWT + localStorage）但 UI、路由、功能集完全隔离 |

### 4.2 认证技术改造点

1. `users` 表：`role` 增加 `student`；新增 `real_name`（学生真实姓名，教师识别用）、`grade_band`（初中/高中）、`grade`（年级）、`class_id`（所属班级）、`must_change_password`（首登改密标记）；
2. 登录请求带 `portal` 参数（`teacher` / `student`）：`POST /api/v1/auth/login` 增加 portal 校验——教师门户拒绝 student 角色登录，学生门户拒绝 teacher/admin；
3. JWT payload 增加 `portal` 声明；新增两个 FastAPI 依赖：
   - `require_teacher`：role ∈ (teacher, admin)
   - `require_student`：role == student
   - 教师端路由组挂 `require_teacher`，学生端路由组挂 `require_student`，交叉访问 403；
4. 学生账号生命周期：
   ```
   教师创建班级（生成 6 位邀请码）→ 学生在学生门户"加入班级"（邀请码+姓名+自设密码）
   或：教师批量导入名册（CSV：姓名/学号）→ 系统生成初始账号（学号为用户名）→ 学生首登改密
   → 学生转班/毕业：教师端管理（停用/迁移）
   ```
5. 密码策略：学生密码最短 6 位（现状），教师 8 位（顺手收紧）；教师可重置本班学生密码；
6. 审计：学生登录不作审计（量大无价值），教师/管理员的治理动作审计保留现状。

### 4.3 为什么不建议物理分库/分表

评估过"学生教师完全两套账号表"，否决：作业闭环要求 `assignments → submissions → answer_records` 跨师生外键关联，分表会把所有查询变成跨库 join 或数据同步，复杂度翻倍且没有安全收益——安全边界靠**角色+门户+路由组**实现足够（学校内网场景）。此决策记为 ADR，若未来多校 SaaS 化再引入租户隔离。

## 六、数据模型扩展设计

新增/改动以迁移脚本推进（`migrations/V3__platform_base.sql` 起），延续幂等规范。

### 6.1 现有表扩展

```sql
-- V3：users 扩展（学生角色与归属）
ALTER TABLE users
    ADD COLUMN real_name VARCHAR(64) NULL COMMENT '真实姓名（学生必填）',
    ADD COLUMN grade_band VARCHAR(8) NULL COMMENT '初中/高中',
    ADD COLUMN grade VARCHAR(16) NULL COMMENT '年级，如 初二/高一',
    ADD COLUMN class_id BIGINT NULL COMMENT '所属班级',
    ADD COLUMN must_change_password TINYINT NOT NULL DEFAULT 0,
    ADD COLUMN student_no VARCHAR(32) NULL COMMENT '学号（班内唯一）';

-- V3：questions 扩展（从"分类样本"升级为"完整题目"）
ALTER TABLE questions
    ADD COLUMN options_json JSON NULL COMMENT '结构化选项 [{key:"A",text:...}]',
    ADD COLUMN answer VARCHAR(512) NULL COMMENT '参考答案（客观题为选项键）',
    ADD COLUMN analysis TEXT NULL COMMENT '解析',
    ADD COLUMN difficulty TINYINT NULL COMMENT '难度 1~5',
    ADD COLUMN grade_band VARCHAR(8) NULL COMMENT '初中/高中',
    ADD COLUMN grade VARCHAR(16) NULL,
    ADD COLUMN knowledge_node_id BIGINT NULL COMMENT '挂接知识点树节点（迁移期与 knowledge_point 文本并存）',
    ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'published' COMMENT 'draft/pending/published',
    ADD COLUMN created_by BIGINT NULL COMMENT '录入教师';
```

### 6.2 新增表

```sql
-- 班级
CREATE TABLE IF NOT EXISTS classes (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(64) NOT NULL COMMENT '班级名，如 初三(2)班',
    grade_band VARCHAR(8) NOT NULL,
    grade VARCHAR(16) NOT NULL,
    invite_code CHAR(6) NOT NULL UNIQUE,
    created_by BIGINT NOT NULL,
    is_active TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 知识点树（先二级：学科 → 一级知识点；预留 parent_id 支持未来细化到章节）
CREATE TABLE IF NOT EXISTS knowledge_nodes (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    parent_id BIGINT NULL,
    subject VARCHAR(32) NOT NULL,
    grade_band VARCHAR(8) NULL COMMENT 'NULL=通用',
    name VARCHAR(128) NOT NULL,
    level TINYINT NOT NULL DEFAULT 1,
    is_active TINYINT NOT NULL DEFAULT 1,
    UNIQUE KEY uq_node (subject, grade_band, name, level)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- 初始化：从现有 labels.json 的 50 个 学科::知识点 自动播种（模型输出兼容映射）

-- 试卷 / 试卷题目
CREATE TABLE IF NOT EXISTS papers (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(128) NOT NULL,
    subject VARCHAR(32) NOT NULL,
    grade_band VARCHAR(8) NOT NULL,
    created_by BIGINT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS paper_questions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    paper_id BIGINT NOT NULL,
    question_id BIGINT NOT NULL,
    order_no INT NOT NULL,
    score DECIMAL(5,1) NOT NULL DEFAULT 0 COMMENT '0=按题型默认分',
    UNIQUE KEY uq_paper_question (paper_id, question_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 作业/考试
CREATE TABLE IF NOT EXISTS assignments (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    paper_id BIGINT NOT NULL,
    class_id BIGINT NOT NULL,
    title VARCHAR(128) NOT NULL,
    mode VARCHAR(16) NOT NULL DEFAULT 'homework' COMMENT 'homework/exam',
    due_at DATETIME NULL,
    allow_self_check TINYINT NOT NULL DEFAULT 1 COMMENT '主观题自评开关',
    created_by BIGINT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_assignments_class (class_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 学生提交（一人一次作业一条）
CREATE TABLE IF NOT EXISTS submissions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    assignment_id BIGINT NOT NULL,
    student_id BIGINT NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'in_progress' COMMENT 'in_progress/submitted/checked',
    auto_score DECIMAL(6,1) NULL,
    final_score DECIMAL(6,1) NULL,
    submitted_at DATETIME NULL,
    UNIQUE KEY uq_submission (assignment_id, student_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 作答记录（学情数据底座；练习/重练也写此表，source 区分）
CREATE TABLE IF NOT EXISTS answer_records (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    submission_id BIGINT NULL COMMENT '作业/考试作答；自主练习为 NULL',
    student_id BIGINT NOT NULL,
    question_id BIGINT NOT NULL,
    answer VARCHAR(512) NULL,
    is_correct TINYINT NULL COMMENT '客观题判分；自评主观题 1/0；NULL=未判',
    source VARCHAR(16) NOT NULL DEFAULT 'assignment' COMMENT 'assignment/practice/wrong_redo',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_records_student_q (student_id, question_id),
    INDEX idx_records_question (question_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**错题本不单独建表**：`answer_records` 中 `is_correct=0` 的去重集合即错题本（"已掌握"标记加一张小表 `wrong_book_marks(student_id, question_id, resolved_at)`）。统计口径（掌握度 = 该知识点下学生正确率）全部 SQL 聚合，与现有 `FeedbackStore.analysis` 同风格。

## 九、题库自动化闭环与模型演进

题库自动化是平台的核心引擎，平台反过来喂养模型——**计划必须保证这条环不被新功能打断**：

1. **录入端更准**：教师确认流（T4）天然产生高质量人工标注（labels_source=manual），管道已在改进计划 WP-F 建好——平台上线后人工标签占比会自然上升，题型"规则标签天花板"随之松动；
2. **使用端更准**：学生真实错误率成为题目与知识点的质量信号——错误率异常的题自动进复核队列（T13），复核修正既修题库也修训练数据；
3. **模型侧演进队列**（按性价比排序，每项独立 ADR）：
   - 知识点树挂接后，训练标签从 50 个一级类逐步对齐树节点（数据攒够再训，门禁兜底）；
   - 学段字段积累后，评估"分学段训练 vs 单模型+学段特征"（ADR，不预设立场）；
   - 远期可选：难度预测头（用作答数据训练，辅助组卷）、错因分类——均为增量实验，不阻塞平台功能；
4. **门禁不变**：任何新版本训练依旧走 golden 评估 + 质量门禁 + 热重载激活，平台流量无感切换。

## 十、师生端 UX 适配原则

| 维度 | 教师端 | 学生端 |
| --- | --- | --- |
| 终端 | 桌面优先（≥1280px），兼容平板 | **移动优先（375px 起）**，桌面自适应 |
| 视觉 | 蓝白教研风（延续现有 #2563EB），信息密度高，表格/矩阵为主 | 明快配色（每学科一色）、卡片化、大按钮（≥44px 触控）、进度与星级可视化 |
| 语言 | 专业术语（知识点矩阵、置信度、复核队列） | 学生语言（"薄弱点"→"需要加练"、"掌握度"→"星级"） |
| 关键交互 | 批量操作、快捷筛选、Excel 导入导出 | 逐题滑动作答、即时对错反馈、错题一键重练 |
| 性能预期 | 列表分页 + 服务端筛选 | 首屏 < 1s（题目文本轻量，无重资源） |
| 防护 | 治理操作二次确认 + 审计 | 防重复提交（submission 唯一键）；截止时间后只读 |

无障碍与合规底线：学生为未成年人——**只收集姓名/学号/班级/作答数据，不收集手机号等联系方式**；登录不放第三方 SDK；数据不出本地部署环境（私有化交付即合规卖点）。

## 十一、风险与关键决策点

| # | 风险/决策 | 影响 | 对策 |
| --- | --- | --- | --- |
| 1 | 知识点体系只有 50 个一级类，学情分析颗粒度粗 | 学情价值打折 | M0 先上"学科::学段"二维树（现有标签自动播种）；细化到章节靠教师日常标注积累，**不一次性人工编大表** |
| 2 | 主观题批改 | 工作量与体验 | MVP 用"自评+教师抽改"；**明确不做 AI 批改主观题**（准确率风险与算力成本，见第十二节） |
| 3 | 模型是否区分初高中 | 分类精度 vs 复杂度 | 先不加学段到模型（题目元数据区分）；学段数据攒够后做 ADR 对比实验，门禁兜底 |
| 4 | 学生规模后的并发 | 性能 | 一个班 50 人同时交作业是峰值场景，单机单体绰绰有余；作答提交做幂等（唯一键）防连点 |
| 5 | 前端形态（继续原生 HTML vs Vue3） | 开发效率 | M0~M3 继续原生多页（快、零构建链）；M4 末评估，页面 >10 且迭代痛苦再立 Vue3 ADR |
| 6 | 未成年人数据合规 | 法律 | 数据最小化 + 本地化部署 + 无第三方 SDK；交付时附《数据说明》一页纸 |
| 7 | 单人开发周期失控 | 交付 | 严格按 M 顺序，M1/M2 各有独立可演示产出；学生端作答页是全计划最高优先级单点 |
| 8 | 教师录入意愿（冷启动） | 平台空转 | T4 确认流必须做到"比手工标快"（<30s/题）；提供 Excel 批量导入兜底已有题库迁移 |

## 十二、明确不做的事

| 不做 | 原因 |
| --- | --- |
| AI 批改主观题（作文/解答） | 准确率不可控、算力成本高、教育场景容错低；自评+抽改已满足 MVP |
| 微服务/多租户 | 单校部署规模，沿用既有 ADR |
| 家长端/消息推送（短信/微信通知） | 涉及第三方与合规审批，二期再说；MVP 用"截止时间展示"替代催办 |
| 通用考试防作弊（切屏监控/摄像头） | 侵入性强且不可靠；作业场景靠题库差异卷（后续可加"同知识点随机抽题组卷"变体） |
| 大模型（LLM）引入录入/讲解 | 分类场景 BERT 已达标且成本为零；LLM 作为 ADR 备选不启用 |
| 学生社交功能（评论/排行公开） | 未成年人保护与攀比风险；学情只对学生本人和其教师可见 |

## 结语

这份计划的所有扩展都建立在已验证的基座上：认证扩展而非重造、题库扩展而非迁移、组卷增强而非重写、查重复用为推荐、再训练管道直接衔接复核工作台。最大新增量是**学生端**——它把平台从"教师的工具"变成"师生数据闭环"，而闭环里沉淀的每一份作答数据，既服务于学情，也在喂养更准的分类模型。按 M0→M4 推进，8~9 周后你得到的不是一组功能清单，而是一条能自己转起来的数据飞轮。
