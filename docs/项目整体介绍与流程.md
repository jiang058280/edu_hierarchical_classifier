## 一、项目是什么

本项目正在从“教育题目层级分类系统”升级为 **基于 RAG 与学情画像的个性化智慧学习平台**。当前已实现的核心能力是对题目文本完成 **学科 → 题型 → 知识点** 三级分类；目标形态是在此基础上加入可治理的教育知识库、带引用的知识问答、可解释学情画像和个性化巩固推荐。

- **技术内核**：本地微调的 `bert-base-chinese`，采用 **共享主干 + 多任务三头** 结构，一次前向传播同时输出三级结果（避免串行级联的耗时）。
- **业务价值**：题库自动标注 → 教学资料知识化 → 学生可信问答 → 学情诊断 → 个性化练习 → 效果反馈。
- **分类模型定位**：BERT 分类器是教育元数据引擎，为 RAG 检索过滤、错题聚合、画像计算和推荐重排提供结构化标签。
- **RAG 定位**：RAG 是目标产品的核心交互与内容组织能力，回答必须基于教师审核资料并返回来源，不作为无依据的通用聊天工具。
- **项目定位**：从“分类模型 Demo”演进为“企业级教育 RAG 单体应用”的完整工程实践；模型核心保留，工程外壳、知识库和学习闭环持续扩展。

## 三、总体架构

```
浏览器
 ├── static/index.html（分类页：录题/示例/反馈/统计/查重提示）
 └── static/admin.html（治理工作台：版本列表/激活/回滚/统计/Bad Case）
        │  fetch（限流 120 次/分/客户端 + Pydantic 校验 ≤4000 字）
        ▼
FastAPI（app.py 薄入口，lifespan 预热完成后才接流量）
   └── edu_core.api（classify / questions / stats / models / pages 五组路由）
        ▼
ClassificationService（application 层编排，进程级单例）
   ├─ HierarchicalPredictor.predict()      inference 层：active 版本权重，GPU/int8 自适应
   ├─ confidence 分级                       ≥0.80 high / 0.60~0.80 medium / <0.60 low
   ├─ ClassificationStore.insert()          留痕：三级预测 + 置信度 + model_version + 耗时
   ├─ StatsStore.bump_processed()           daily_stats 按日原子累计
   └─ QuestionDedupIndex（dedup 层）        Milvus 768 维 COSINE 查重（可降级跳过）
        ▼
MySQL 8.4（6 张业务表，唯一业务事实源）
```

### edu_core 分层职责

| 分层 | 模块 | 职责 | 关键约束 |
| --- | --- | --- | --- |
| config | `settings.py` / `preflight.py` / `logging_config.py` | pydantic-settings 配置（`EDU_` 前缀环境变量）、启动前文件系统校验、结构化日志 | preflight fail-fast，缺资产拒绝启动 |
| inference | `model.py` / `predictor.py` | 三头模型结构；版本化加载 + 量化 + 推理 + `embed()` 向量提取 | 权重缺失抛 `ModelArtifactError`，绝不带随机头服务 |
| data | `dataset.py` | raw JSON 清洗/标签映射/小类合并/分层划分 | 全部纯函数，可被 pytest 直接覆盖 |
| training | `train.py` | 多任务加权损失训练 + 早停 + 版本产物落盘 | 产物写 `models/versions/<ver>/` |
| application | `service.py` / `confidence.py` / `factory.py` | 分类/反馈/题库/组卷编排；置信度分级；进程级单例装配 | 不写 SQL、不感知 HTTP |
| storage | `runtime_schema.sql` / `bootstrap.py` / `stores.py` | 集中 DDL + 建库 + 5 个 Store | DDL 集中单文件，不引入 Alembic |
| governance | `model_versions.py` | 版本注册/激活/回滚/查询（STAGED→ACTIVE→ARCHIVED） | MySQL 注册表 + 单行 active 指针是唯一事实源 |
| quality | `evaluation.py` / `gate.py` | golden set 回归评估；门禁判定（纯函数） | 门禁不过 = 不激活 |
| dedup | `milvus_client.py` | 题目向量索引 + 相似检索 | 懒连接，任何失败降级跳过，不阻塞主链路 |
| observability | `tracing.py` | 阶段耗时记录 | — |
| api | `classify` / `questions` / `stats` / `models` / `pages` + 限流 + 错误处理 | 路由与横切面 | 同一 router 以 `/api/v1` 与 `/api` 双前缀注册 |

**设计原则**：入口越薄越好（app.py 只做装配）；核心链路不允许静默降级（模型资产缺失即 fail-fast）；增强功能（查重）明确允许降级。

### 目标 RAG 架构（规划 R1～R3）

```text
教师上传教材/讲义 ─┐
题库答案与解析 ────┼→ 清洗/父子分块/指纹 → BGE-M3 → RAG 专用 Milvus collections
标准知识问答 ─────┘                         │
                                             ▼
学生问题 → 教育意图/查询补全 → FAQ + 文档 + 题目混合检索 → Reranker
                                                      │
学生作答记录 → 学情画像 → 知识点/难度/复习优先级 ─────┤
                                                      ▼
                                    证据阈值 → LLM 流式生成
                                                      │
                         来源引用/拒答/Trace/反馈 ←────┘
                                      │
                                      ▼
                         个性化巩固题单 → 新作答 → 画像更新
```

目标分层沿用当前 `edu_core` 风格，并参考 `D:\knowforge-rag-platform`：

| 新分层 | 目标职责 |
| --- | --- |
| `rag/loaders + chunking + indexing` | 文档解析、标准化、父子分块、增量向量化与入库报告 |
| `rag/retrieval` | FAQ/文档/题目多路召回、元数据过滤、融合与重排 |
| `rag/pipeline` | 查询路由、改写、检索、上下文、生成、引用校验和拒答编排 |
| `rag/llm` | OpenAI-compatible 模型客户端与连通性状态，避免绑定厂商 SDK |
| `rag/governance` | 知识库版本注册、激活、回滚及 chunk 有效期管理 |
| `learning_profile` | 结构化掌握度、趋势、画像可信度与薄弱点计算 |
| `recommendation` | 候选题召回、教育策略重排、推荐解释和结果留痕 |

当前分类链路和目标 RAG 链路保持独立服务边界，通过题目标签、知识点树和学生作答数据协作；RAG 故障不得破坏分类、作业和判分主链路。

## 七、模型：结构、训练与推理

### 7.1 模型结构（`edu_core/inference/model.py`）

```
题目文本（max_len=256 token 化）
        ▼
bert-base-chinese 主干（冻结 embeddings + 前 9/12 层，微调后 3 层 + pooler）
        │  pooler_output（768 维）
        ├────────────────┬──────────────────────┐
        ▼                ▼                      ▼
  学科头 Linear     题型头 Linear          知识点头 ResidualMLP
  768 → 9          768 → 3               768→384→128→384→50（双层残差+LayerNorm，dropout 0.25）
        └────────────────┴──────────────────────┘
                         ▼
            一次前向同时输出三级 logits + softmax 置信度
```

- 三头统一 xavier 初始化；一次前向替代串行级联（CPU 推理耗时较管道式直降约 60%）。

### 7.2 训练（`edu_core/training/train.py`）

| 项 | 配置 |
| --- | --- |
| 多任务损失权重 | 学科 0.28（LabelSmoothCE 0.05）/ 题型 0.27（LabelSmoothCE 0.05）/ **知识点 0.45（FocalLoss γ=1.5 + LabelSmooth 0.08，应对类别不均衡与过自信）** |
| 优化 | lr 2e-5、batch 8、epochs 12、warmup 0.1、weight decay 0.01、验证集早停 patience 5 |
| 产物 | `models/versions/<ver>/{三头.pt, manifest.json}`；manifest 记录 `backbone_ref` 指向微调主干目录（复用共享主干，避免每版本复制 400MB） |
| 主干来源 | 最初从本地候选模型（`d:/pycharm/ccpython/toumanfen/003_bert`）评估择优复制而来，原始路径只读留档于 `legacy/user_models/models_path.txt` 与 `config.yaml` |

### 7.3 推理（`edu_core/inference/predictor.py`）

- **版本化加载**：显式传入版本目录，校验 `manifest.json` + 三头权重 + `backbone_ref` 微调权重，**任一缺失抛 `ModelArtifactError` 拒绝服务**；
- **设备自适应**：有 GPU 用 CUDA；CPU 时自动 `quantize_dynamic` 转 **int8**（仅量化 nn.Linear）；
- **进程内有界 LRU 缓存**（512 条，OrderedDict 实现，修复了旧版实例级 `lru_cache` 强引用 self、多 worker 命中率归零的缺陷）；
- **`embed()`**：输出 BERT [CLS] 池化向量（768 维），供 Milvus 查重；
- tokenizer 使用 `AutoTokenizer`（替换已弃用的 `BertTokenizer`）；`torch.load` 全部 `weights_only=True`。

## 八、核心业务流程

### 8.1 服务启动流程（`app.py` lifespan，全部通过后才接流量）

```
① prelight 文件校验（validate_runtime_environment）
     主干目录 / labels.json / 版本目录结构 / manifest 完整性
        ▼
② MySQL schema bootstrap（执行 runtime_schema.sql，建 6 张表）
        ▼
③ active 模型版本校验（MySQL active 指针 → 版本目录存在且齐全，否则拒绝启动）
        ▼
④ 预测器预热（加载 active 版本权重 + 完成一次真实推理，记录延迟）
        ▼
⑤ Milvus 查重索引探测（异步，失败仅告警不阻塞 —— 增强组件允许降级）
```

### 8.2 在线分类主链路（`POST /api/v1/classify`）

```
输入校验（非空、≤4000 字）
    ▼
predictor.predict(text)
    ├─ 归一化空白 → LRU 缓存命中？（命中直接返回，latency=0, cached=true）
    └─ 未命中：tokenizer → 前向 → 三级 softmax → 标签 + 置信度 + latency_ms
    ▼
confidence 分级：平均置信度 ≥0.80 → high；0.60~0.80 → medium；<0.60 → low（附复核建议）
    ▼
classifications 留痕（text_hash + 预览 + model_version + 三级预测 + 置信度 + band + 耗时）
    ▼
daily_stats 按日原子累计（upsert）
    ▼
响应：subject / q_type / knowledge / confidences（旧契约）
      + id / avg_confidence / band / review_hint / model_version / latency_ms / cached
```

### 8.3 题目录入与语义查重（`POST /api/v1/questions`）

```
题目入库（questions 表，text_hash 去重辅助）
    ▼
dedup.upsert_question()：predictor.embed() 生成 768 维向量 → 写 Milvus
    ▼
dedup.search_similar()：top-K 相似检索（COSINE），相似度 ≥0.95 的结果作为"疑似重复题"提示返回
    ▼
Milvus 不可用 → available=False，跳过查重，主链路照常完成（明确降级）
```

### 8.4 反馈与 Bad Case 再训练闭环

```
用户点"正确/错误"（或带 corrected_* 修正值）→ POST /api/v1/feedback
    ▼
feedback 表落库，外键关联 classification_id + 记录当时的 model_version
（这是旧版"反馈无法再训练"缺陷的根治：每条反馈都能追溯到具体一次推理与版本）
    ▼
scripts/export_bad_cases.py → eval_sets/bad_cases.json（含 corrected_* 与 review_status）
    ▼
人工复核 → 复核通过样本并入训练集
    ▼
scripts/train_model.py --version vX → rebuild_model_version.py --gate --activate
    ▼
门禁对比旧版指标后激活，旧 ACTIVE 自动归档（可回滚）
```

### 8.5 模型版本治理状态机（`edu_core/governance/model_versions.py`）

```
训练产物 models/versions/<ver>/
        │ register_version()（校验三头 + manifest + backbone_ref 齐全）
        ▼
     STAGED ── golden set 评估 ── 质量门禁 ──通过──► ACTIVE（服务加载的唯一状态）
        │            │                │                │
        │            │             未通过：阻断，      │ 新版本激活
        │            │             版本停在 STAGED     ▼
        │            └────────────────────────► 旧 ACTIVE → ARCHIVED
        ▼
回滚：rollback_to_previous() / POST /api/v1/models/rollback（激活最近归档版本，激活前强校验文件）
```

- 注册表：MySQL `model_versions` 表 + `active_model_pointer` 单行指针（`CHECK(id=1)` 保证单行）；
- 版本命名：`v{major}.{minor}-{YYYYMMDD}-{HHMMSS}`，迁移基线为 `v0.1-base`；
- 服务启动强校验 active 版本文件齐全，**"线上跑的是哪个版本"永远有唯一答案**。

### 8.6 发布验收流水线（`scripts/verify_release.py`）

```
guardrails（反模式检查）→ pytest（30 条）→ 数据资产（labels + golden set）
    → 模型版本目录规范（manifest 有效性）→ MySQL 表结构就绪
        ▼
reports/verification/v1_release_latest.json
（最新一次 2026-09-05 21:27 全部通过，30 passed）
```

### 8.7 目标个性化 RAG 学习闭环（规划）

```text
① 教师上传讲义并发布 ACTIVE 知识库版本
② 学生完成作业，answer_records 记录客观作答结果
③ LearningProfileService 按知识点计算掌握度、趋势和可信度
④ 学生从错题发起“为什么错”，服务端补全题目与匿名画像上下文
⑤ FAQ/教材/题目解析多路检索，按学段、年级和知识点过滤后重排
⑥ 证据充足：LLM 返回带引用讲解；证据不足：明确拒答或提示教师补充资料
⑦ RecommendationService 召回并重排 5～10 道巩固题，展示推荐原因
⑧ 学生完成练习，结果回写 answer_records 并刷新画像
⑨ 教师端查看个人/班级掌握矩阵、需重讲知识点和 RAG Bad Case
```

推荐不是单纯的向量相似题：候选分数综合薄弱程度、语义相关度、难度适配、遗忘优先级和题目质量，并扣除近期重复与近似重复。LLM 负责解释推荐和组织辅导语言，规则与检索分数负责最终选题。

## 十、存储设计

### MySQL（`edu_core/storage/runtime_schema.sql`，6 张表，DDL 集中管理）

| 表 | 职责 | 关键设计 |
| --- | --- | --- |
| `model_versions` | 版本注册表 | version 唯一；manifest_json / metrics_json 用 JSON 列；status = STAGED/ACTIVE/ARCHIVED |
| `active_model_pointer` | active 指针 | 单行表 `CHECK(id=1)`，语义对齐 knowforge 的知识库 active 指针 |
| `classifications` | 每次推理一条留痕 | text_hash(SHA256) + 500 字预览 + 三级预测/置信度 + band + latency + cached；三个索引（时间/版本/哈希） |
| `questions` | 题库 | 替代旧版内存 `question_db`；source 标记 manual/ai_input/import；status 草稿/发布/归档 |
| `feedback` | 反馈 | **classification_id 关联推理记录** + model_version + corrected_* 修正字段 —— 再训练闭环的数据入口 |
| `daily_stats` | 按日累计统计 | stat_date 主键，原子 upsert（根治旧版 stats.json 单日覆盖丢历史） |

### Milvus（`edu_question_dedup` collection）

- 只存向量与最小元数据（业务事实仍在 MySQL，边界清晰）；
- 768 维 COSINE，阈值 0.95，题库 id 作为主键（auto_id=False）；
- 不可用时整体降级跳过，不影响分类主链路。

### 目标 RAG 存储（规划）

RAG 不复用 `edu_question_dedup`，而是建立职责清晰的独立索引：

| 存储 | 内容 | 用途 |
| --- | --- | --- |
| `edu_rag_documents` | 教材、讲义、知识点说明、公式和解题方法的 chunk | 教学资料问答与概念讲解 |
| `edu_rag_questions` | 题干、答案、解析、题型、知识点和难度 | 错题解释、相似题和巩固题召回 |
| `edu_rag_faq` | 教师审核后的标准问题与答案 | 高置信直接回答，降低延迟与幻觉 |
| MySQL RAG 表 | 文档、版本、会话、消息、Trace、反馈和画像快照 | 唯一业务事实源、审计与可复现 |

Milvus metadata 至少包含学科、学段、年级、知识点、资料状态、知识库版本和角色范围。姓名、账号及原始作答记录不得进入向量库；个性化问答仅向 LLM 注入匿名、最小化的结构化画像摘要。

## 十六、严格分析：亮点与不足

### 做得好的（相对同类练手项目）

1. **模型内核扎实且被完整保留**：多任务三头 + FocalLoss/LabelSmooth 的损失设计、冻结策略、量化推理，都是从数据里调出来的（max_len 128→256 有数据依据），没有为改架构而推翻。
2. **"唯一事实源"贯彻得干净**：模型版本以 MySQL 注册表 + active 指针为准；业务数据以 MySQL 为准；Milvus 明确定位为可降级增强——核心链路与增强链路的降级策略边界清晰。
3. **fail-fast 纪律**：preflight → 注册校验 → 激活校验 → 启动校验四处设卡，"随机头静默服务"这类最隐蔽的事故路径被彻底封死。
4. **反馈闭环打通了最后一公里**：反馈强制关联推理留痕与版本，Bad Case 可导出复核再训练——多数 Demo 死在这一步。
5. **反模式防回流**：guardrails 把旧版的每个坑（Gradio 私有 API、CORS `*`、硬编码路径、os.chdir、未锁依赖）变成可执行检查。
6. **文档与代码一致**：README 的架构描述与实际代码逐文件对得上（本次分析已核对）。

### 当前不足与风险（按优先级）

> 本节原始审计结论保留用于说明企业化改造起点；其中鉴权、迁移、热重载等事项已有后续版本完成。面向新的教育 RAG 定位，新增的首要差距如下。

| 新增差距 | 影响 | 对应计划 |
| --- | --- | --- |
| 尚无教学资料入库、切分与知识库版本 | 无法形成可追溯的 RAG 证据底座 | R1 |
| 当前 Milvus 只做 BERT CLS 题目查重 | 不适合作为文档问答的主检索链路 | R1/R2：独立 collection + BGE-M3 + Reranker |
| 尚无问答编排、引用校验与拒答 | 不能称为可信教育 RAG | R2 |
| 当前学情分析仅有简单聚合规划 | 无法稳定驱动个性化教学 | R3：掌握度、趋势、可信度和时间衰减 |
| 相似题推荐缺乏教育重排 | 容易重复、难度失配，无法解释推荐原因 | R3：多路召回与可复现评分 |
| 未建立 RAG 专项评测 | 无法证明召回、忠实度和拒答可靠性 | R2/M4 |

| # | 问题 | 严重度 | 说明 |
| --- | --- | --- | --- |
| 1 | **无 CI**（`.github/` 不存在） | 🟠 | 门禁/guardrails/pytest 都有脚本但没有流水线强制，全靠人工自觉执行 `verify_release.py` |
| 2 | **无鉴权体系** | 🟠 | 全部接口无登录/RBAC；治理接口（激活/回滚/删题）裸奔。私有化交付前必须补（改造计划 Phase 4/5 范畴） |
| 3 | **题型标签是规则推断的** | 🟠 | `infer_question_type()` 用正则从文本推断训练标签，模型学到的是规则本身，题型 F1 的上限即规则准确率；需人工复核数据逐步替换 |
| 4 | **知识点天花板** | 🟠 | F1 55.5%（acc 73.9%），根因是样本量（增强后 6,901 条）与 50 类的类别粒度；层级信息未被利用（知识点头不感知学科，未做非法组合 mask） |
| 5 | **数据溯源两套口径** | 🟡 | `cleaning_report.json`（3,252）与 `labels.json`（6,901）不一致，增强步骤的参数与版本未留痕；无数据版本管理（DVC/快照清单） |
| 6 | **落盘评估报告是冒烟口径** | 🟡 | `v0.1-base_evaluation.json` 实为 50 条冒烟报告；作为门禁基线证据链偏弱，建议重跑全量 300 条 |
| 7 | **模型与 Web 同进程** | 🟡 | 预测器在 API 进程内单例加载，无法独立扩容/重载；`models/{version}/activate` 后需重启服务才生效 |
| 8 | **无 DB 迁移机制** | 🟢 | DDL 集中在 `runtime_schema.sql` + 幂等 `CREATE IF NOT EXISTS`，改表结构需手工对齐（生产化时应升格为迁移基线） |
| 9 | **目录卫生** | 🟢 | `.edge_profile/`、`.huggingface_cache/` 等缓存目录虽已 gitignore，但仍占磁盘；`logs/` 里残留旧版运行时产物 |
| 10 | **`config.yaml` 成孤儿配置** | 🟢 | 主链路已改走 pydantic-settings（guardrails 禁止主链路读它），但文件仍在且含个人路径——建议要么删除、要么明确标注"溯源记录"用途 |

### 结论

> 分类模型与企业化主干已经为教育 RAG 提供了可靠底座。下一阶段的主任务不再是继续堆叠分类页面，而是依次完成 **作业数据闭环、教育知识库、可信 RAG 问答、可解释学情画像和个性化巩固推荐**，最终形成“诊断—讲解—练习—再诊断”的闭环。详细任务、工期与验收标准以《剩余工作总计划.md》v1.2 为准。
