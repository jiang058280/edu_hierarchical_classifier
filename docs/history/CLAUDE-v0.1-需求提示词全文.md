## 二、项目概述

### 1. 背景

在线教育、智能题库、自动化组卷等场景中，海量题目需要准确归类，以实现精准推荐、智能检索和学情分析。现有系统多仅支持单一维度分类（如只分学科），无法满足"先分学科、再分题型、再分知识点"的精细化需求。

### 2. 目标

构建层级文本分类系统，对输入题目文本自动完成三级分类：

text

```
输入：题目文本
  ↓ 第一级：学科分类（数学、英语、物理、化学、生物、历史、地理、政治、语文等）
  ↓ 第二级：题型分类（如英语→完形填空/单选题/阅读理解；数学→选择题/填空题/解答题）
  ↓ 第三级：知识点分类（如数学→函数/三角函数/数列；物理→力学/电磁学/热学）
输出：三级分类标签 + 各级置信度
```



### 3. 定位

练手/演示级项目，交付物为可在本地笔记本电脑上运行的交互式 Demo（CPU 优先，GPU 可选）。

### 4. 核心业务价值

- 提升题库管理效率：自动标注新入库题目，减少人工成本
- 支撑智能推荐：根据学生薄弱知识点精准推送题目
- 助力学情分析：分析学生在各学科/题型/知识点的表现

## 三、功能需求

### 1. 核心功能模块

| 模块       | 功能描述                   | 输入                | 输出                          |
| :--------- | :------------------------- | :------------------ | :---------------------------- |
| 学科分类   | 识别题目所属学科           | 题目文本            | 学科标签（如"数学"）          |
| 题型分类   | 在确定学科后识别具体题型   | 题目文本 + 学科标签 | 题型标签（如"选择题"）        |

- **API 调用（可选）**：提供 RESTful 接口供其他系统调用。

- 响应时间：单次预测 < 3 秒（CPU 环境），可通过量化 / ONNX 优化达成。
- 准确率：学科 / 题型 / 知识点分类指标均 > 85%，越高越好（视数据量而定）。
- 可扩展性：支持新增学科 / 题型 / 知识点，无需重构整个系统。
- 磁盘隔离：所有项目相关文件强制位于 D 盘，不允许写入 C 盘。

## 五、模型选型与迁移策略（核心改动）

### 1. 模型前置评估（必做步骤，项目启动第一步）

由于您已有多个训练好的文本分类模型，本项目不直接从头训练，而是采用以下流程：

**Step 1：识别候选模型路径（无需移动文件）**

- 您已在 **Trae** 中打开了存放训练好的模型的文件夹，AI 将直接通过该上下文识别模型文件路径。
- **严格禁止**将模型文件复制或移动到任何新建目录中，保持其原始位置绝对不变。
- AI 在分析时，需先扫描您在 Trae 中打开的文件夹，读取其中的模型文件，自动识别其架构（如 BERT、RoBERTa、TextCNN 等），无需用户提供 `model_meta.json`。
- 若模型文件格式多样（如 `.bin`、`.pt`、`.pth`），AI 需自动适配加载方式。
- 模型识别完成后，在 `config.yaml` 中记录其原始路径（仅用于读取评估）。

**Step 2：新建项目文件夹**

- 在 D 盘新建 `D:\edu_hierarchical_classifier\`，并按文档第八节的结构创建所有子文件夹。
- 虚拟环境创建在 `D:\edu_hierarchical_classifier\venv\`。

**Step 3：运行评估脚本（`src/evaluate_models.py`）**

- 在验证集（从 K-12EduBench 抽取 500~1000 条）上，**冻结模型主干**，仅提取 CLS 池化向量。
- 训练一个轻量逻辑回归头，评估其在本项目标签上的 **宏平均 F1**。
- 同时测量**单条推理耗时**（在 CPU 上）。
- 评估报告（含每个模型的 F1、推理速度、参数量、推荐指数）输出到 `logs/evaluation_report.json`。

**Step 4：筛选标准（硬性 + 软性）**

- **硬性门槛**：单条推理耗时 < 1.5 秒（留出余量给后续分类头）。
- **软性择优**：在通过门槛的模型中，选择 F1 最高的作为"基线模型"。
- 若所有模型均不满足耗时要求，则自动下载轻量级中文预训练模型（如 `distilbert-base-chinese`）作为兜底，并记录日志。

**Step 5：主干提取与迁移（唯一写入操作）**

- 评估确定最佳模型后，**仅将该模型的主干权重（Backbone）复制**到项目目录 `D:\edu_hierarchical_classifier\models\pretrained_backbone\` 下，作为后续微调的初始权重。
- 原始模型文件始终保持不动，项目文件夹内只存放"被选中用于本项目"的那一份拷贝。

### 2. 模型迁移与结构调整

- **共享主干**：沿用选中的基线模型主干（Backbone）权重，**冻结前 80% 层**，仅微调后 20% 层。
- **三个独立分类头**（替换原分类头）：
  - 学科头（输出维度 = 学科类别数，如 9）
  - 题型头（输出维度 = 该学科下的题型数，可设计为按学科动态路由）
  - 知识点头（输出维度 = 该学科下的知识点数）
- **训练方式**：多任务学习，同时优化三个头的交叉熵损失，加权求和后反向传播。这样一次前向传播同时得到三级结果，避免串行级联耗时，**CPU 推理耗时直降约 60%**。

### 3. 兜底方案

若评估后所有候选模型均不可用，AI 可自主推荐合适的轻量中文预训练模型（如 `microsoft/MiniLM-L12-H384-uncased` 的中文版或 `distilbert-base-chinese`），并给出选择依据。

## 六、技术方案

### 1. 整体架构（共享主干 + 多任务头）

text

```
用户输入（题目文本）
        │
        ▼
共享编码器（Backbone，冻结 80% 层）
  输出：文本语义向量 [CLS] (768维 或 384维)
        │
        ├──────────────┬──────────────┐
        ▼              ▼              ▼
  学科分类头      题型分类头     知识点分类头
  线性+Softmax   线性+Softmax   线性+Softmax
  输出：学科      输出：题型      输出：知识点
  + 置信度        + 置信度        + 置信度
        │              │              │
        └──────────────┴──────────────┘
                     ▼
              返回三级分类结果 + 置信度
```



### 2. 硬件策略（CPU 优先，GPU 按需）

- **默认运行环境**：CPU。为加速，采用以下优化：
  - **动态量化**：推理时使用 `torch.quantization.quantize_dynamic` 将模型转为 int8，速度提升 2~4 倍，精度损失 < 1%。
  - **ONNX Runtime**（可选）：若量化后仍不够，导出为 ONNX 格式，利用 CPU 底层指令集进一步加速。
  - **批处理缓存**：在 Gradio 后端使用 `@lru_cache` 对相同输入做缓存。
  - **推理时固定 batch_size=1**，避免 CPU 内存溢出。
  - **关闭梯度计算**：使用 `with torch.no_grad():` 节省内存和计算。
- **GPU 启用条件**：若实测 CPU 推理仍 > 3 秒，再按需启用 NVIDIA 显卡。此时才考虑安装 CUDA 版 PyTorch（详见第十二节附录）。代码中通过 `device = torch.device("cuda" if torch.cuda.is_available() else "cpu")` 自动适配，无需修改业务逻辑。

## 七、训练与推理流程

### 1. 训练流程

1. 加载清洗后的数据集（从 `data/processed/` 读取）。
2. 按学科分组，统计各级标签类别数。
3. 构建多任务模型（共享主干 + 三头），主干加载从您原始模型复制来的权重。
4. 设置 `config.yaml` 中的训练参数（学习率、batch size、epochs 等）。
5. 在训练集上微调，使用验证集早停（patience=3）。
6. 保存模型：
   - 主干权重保存到 `models/pretrained_backbone/`
   - 学科头保存到 `models/heads/subject_head.pt`
   - 题型头保存到 `models/heads/type_head.pt`
   - 知识点头保存到 `models/heads/knowledge_head.pt`

### 2. 推理流程

1. 加载模型及分类头。
2. 根据 `config.yaml` 中的 `use_dynamic_quantization` 决定是否启用动态量化。
3. 根据 `config.yaml` 中的 `device` 决定使用 CPU 还是 GPU。
4. 输入题目文本 → 编码器获得向量 → 分别通过三个头获得三级标签及 Softmax 概率。
5. 返回结果（标签 + 置信度）。

### 3. 推理代码核心逻辑（`src/predict.py`）

python

```
def predict(text: str, config: dict) -> dict:
    device = torch.device(config["hardware"]["device"])
    model = load_model(config).to(device)
    model.eval()
    
    with torch.no_grad():
        inputs = tokenizer(text, return_tensors="pt").to(device)
        outputs = model(inputs)
        subject = outputs["subject"].argmax().item()
        q_type = outputs["question_type"].argmax().item()
        knowledge = outputs["knowledge"].argmax().item()
        # 计算置信度（Softmax 概率）
        conf_subject = outputs["subject"].softmax(dim=-1).max().item()
        conf_type = outputs["question_type"].softmax(dim=-1).max().item()
        conf_knowledge = outputs["knowledge"].softmax(dim=-1).max().item()
    
    return {
        "subject": id2subject[subject],
        "question_type": id2type[q_type],
        "knowledge_point": id2knowledge[knowledge],
        "confidence": {
            "subject": conf_subject,
            "question_type": conf_type,
            "knowledge_point": conf_knowledge
        }
    }
```

**解决方案：postMessage 桥接**（`postMessage` 不受同源限制，跨源可用）：

```
用户在 iframe 输入题目 → 点「开始分类」→ Gradio 真实推理（src/predict.py）
   ↓ 结果渲染在 iframe（原逻辑不变）
   ↓ 同时 app.py 的 HEAD_JS 追加一行：window.parent.postMessage({type:'edu-classify', result:{...}}, '*')
platform.html 监听 message 事件
   ↓ 更新右侧：本次分类摘要 + 三级标签确认卡（含置信度）+ 追加到分类历史最新一条
```

- iframe 页面加载完成后向父窗口发送 `{type:'edu-ready'}` 心跳，供父页面判断后端服务是否存活（P3）。
